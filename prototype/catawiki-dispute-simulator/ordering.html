Both events use the same schema ID. The key affects which partition gets them; Kafka preserves order within each partition.

i

Keep the two jobs separate: Schema Registry stores the contract. The serializer reuses schema ID 101 and puts it in each encoded record; the record travels directly to Kafka. A consumer deserializer uses that ID to get the writer schema on first use, then caches it. The record key is used for partition routing. With the same key, partitioner, and partition count, related records go to the same partition; Kafka preserves their append order there. With no key, the producer chooses a partition; related records may land apart. There is no order across partitions.
