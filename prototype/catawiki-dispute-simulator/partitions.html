This demo illustrates incoming writes outpacing P0 leader throughput. Records are deliberately routed to P0 here; Kafka has no generic fixed-capacity partition. Would adding another partition help?

i

What to remember: The producer sends DisputeCreated before DisputeResolved. Kafka preserves append order within a partition, but not across partitions. This demo explicitly places the unkeyed events on different partitions; Kafka’s default no-key producer uses a sticky partition for batching. A key normally maps records to a partition, preserving per-key order while that mapping stays stable. Adding partitions can change that mapping, and Kafka does not move existing records. The red outcome is application behavior after the second partition is processed first.
